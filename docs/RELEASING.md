# Выкат tide — ранбук

Как режется релиз: от чистки истории до смока настоящей публичной двери.
Порядок — прожитый, не теоретический; шаги идут именно в этой
последовательности.

## Модель каналов

- **Локальный main** — рабочая история со всем контекстом разработки.
  Наружу она не публикуется никогда.
- **origin/main (публичный репо)** — только squash-коммиты: один коммит на
  выкат, нейтральное сообщение. GitHub Pages собирается из `main:/docs`.
- **Релиз** — тег + gh release + артефакт; brew-формула в тапе едет следом
  как вторичный канал.

## Цикл выката

### 0. Зелёная суита

```bash
python3.12 -m pytest -q      # именно python3.12 — другие шимы бывают без pytest
```

Ноль падений. Дерево — закоммичено (артефакт всё равно режется из коммита,
но `--allow-dirty` — осознанное исключение, не привычка).

### 1. Деанон-гейт — перед ЛЮБЫМ пушем в публичный репо

История локального main несёт личный контекст: имена, хендлы, домашние пути —
не только в файлах, но и в **сообщениях и деревьях коммитов**. Проверяются два
слоя: рабочее дерево и вся публикуемая история (в один из выкатов грязными
оказались деревья 20 из 29 коммитов — squash существует ровно поэтому).

Вердикт должен быть CLEAN. Список личных маркеров живёт у владельца,
не в репо.

### 2. Squash поверх origin/main

Грязная история не публикуется — публикуется один коммит:

```bash
git rev-parse HEAD > /tmp/pre-squash-sha   # страховочный SHA — ДО reset
git fetch origin
git reset --soft origin/main
git commit -m "release: <что в релизе, нейтрально>"
```

Старый HEAD никуда не делся: он в reflog и в страховочном SHA — вернуться
можно всегда (`git reset --hard <sha>`).

### 3. Финальный пробег diff'а

Перед пушем — программный (python) пробег diff'а к origin/main по списку
личных маркеров. Результат — **ноль** вхождений. Затем push main.

### 4. `tide release --yes`

Одна команда режет релиз целиком:

- **прифлайт** — версия, ветка, чистота дерева;
- **ворота регрессии** — суита + `verify --portable` (артефакт обезличен);
- **скан артефакта** — что уезжает в wheel/sdist;
- **тег + gh release** — публикация на GitHub;
- **формула brew** — бамп в тапе.

Известная деталь: push формулы в тап ходит **по ssh**
(`git@github.com:tide-tools/homebrew-tide.git`) — https без кредов падает.
`--dry-run` показывает весь план, ничего не публикуя; `--no-tap` откладывает
brew на потом (тег и gh release — это и есть релиз).

### 5. Pages

Пересобирается сам из `main:/docs`, примерно 40 секунд после пуша. Не
обновился — смотреть последнюю сборку:

```bash
gh api repos/tide-tools/tide/pages/builds/latest
```

### 6. Смок настоящей публичной двери

Не верить своему окружению — пройти дверью пользователя, в изоляции:

```bash
git clone https://github.com/tide-tools/tide /tmp/tide-smoke && cd /tmp/tide-smoke
./install.sh
tide --version
mkdir /tmp/tide-smoke-home && cd /tmp/tide-smoke-home && tide init --git
```

Чистую машину целиком гоняет `packaging/docker/run.sh` (clone → install →
доска, в докере).

## Обновление у своих

- **Клон-канал (главный):** `git pull` + `./install.sh` — переустановка на
  месте. `tide self-update` делает то же с гейтом и откатом (`--rollback`);
  на **editable**-установке разработчика reinstall — фактический no-op:
  файлы на диске и есть боевые.
- **Editable-заусенец:** после бампа версии `tide --version` может показывать
  старые метаданные при живых новых файлах. Файлы правильные; лечится
  переустановкой editable тем же интерпретатором:
  `python3.12 -m pip install -e <checkout>`.
- **Brew-канал вторичен:** несёт только бинарник — скиллы, хуки и доска едут
  в клоне. `brew upgrade tide-tools/tide/tide` после бампа формулы.

## Правило между релизами

Движок у своих стоит editable — каждое сохранение живое. Он обязан оставаться
**импортируемым после каждого сохранения**: сначала модуль — потом импорт,
между правками смок `tide --version`. Подробнее — CLAUDE.md репо.
